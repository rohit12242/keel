### Choices I made that were not specified
- **Table `"user"` kept its ERD name** (reserved word, quoted everywhere) rather
  than renaming to `app_user`. Faithful to the ERD; the cost is quoting.
- **`password_hash` is nullable.** Auth is E-06; inventing a credential now was
  off-limits, so the column exists but is empty on the seed user.
- **`from_parked_idea_id` and `created_by_review_id` are plain uuid columns with
  no FK yet** — the tables they reference (`parked_idea`, `review`) are later
  stories. FKs land with those tables.
- **Enums as real Postgres enum types** (`review_cadence`, `objective_status`,
  `schedule_mode`, `period_kind`) rather than text + CHECK.
- **Non-overlap invariant (4) enforced by an `EXCLUDE` constraint** (needs
  `btree_gist`). Contiguity ("no gaps") is *not* expressible as a cheap
  constraint and is left to the app — noted so it is not mistaken for enforced.
- **`generateSlots` implements fixed schedules only**; flexible/week generation
  throws (the seed uses a fixed segment). Flexible arrives with its story.
- **Migrations are `.cjs` raw SQL** via `pgm.sql`, not the JS builder API —
  clearer and closer to what actually runs. Migration SQL is not "repo.ts", so
  ADR-001's "SQL only in repo.ts" is not violated.

### For your review-gate answer (why local_date and logged_at are separate) [W3-12]
You need: the two answer different questions — `local_date` is *the day the user
meant* (a calendar date, set by the client, never moved — NFR-12 / invariant 2),
`logged_at` is *the instant the row was written* (a timestamptz, server clock).
`tz` records the zone it was logged in. An entry logged at 00:30 for the previous
evening's work must keep the previous day; deriving the day from `logged_at`
would move it. They are separate columns because one is not derivable from the
other. Evidence to point at: the three columns in `effort_entry`, and that
W3-14 takes `local_date`/`tz` from the request body, never from `now()`.

## W3-13 — GET /day/{date}

### What exists now
- `GET /day/{date}` (`src/app/day/[date]/route.ts`) returns the contract's `Day`
  shape against real rows. Validates the date (400 on a bad one), 503 if the DB
  is unreachable. No auth (E-06) — the user is the seeded user, via the service.
- `src/modules/today/repo.ts` — the **one** SQL query.
- `src/modules/today/domain/assembleDay.ts` (+ test) — pure: shapes rows into
  `Day`, sums the totals. `rows.ts` holds the row shape (on the domain side so
  the assembler can import it without importing repo).
- `src/modules/objectives/domain/scheduleLabel.ts` (+ test) — the schedule
  label ("FIXED · MON–FRI · 2h 00m PER DAY").
- `src/shared/contract.ts` — typed DTOs for the contract. `src/shared/http.ts` —
  json / problem (RFC 9457) response helpers.

### The query, and the query count
**One query per request.** `getDayRows` issues a single statement (CTEs: active
objectives → covering segment → covering slot → the date's entries with a
per-entry `extra` flag → week-to-date total → next planned date), returning one
row per active objective. The app never loops over objectives issuing more
reads. Verified live: `/day/2026-09-16` (planned Wed) returns the slot + label;
`/day/2026-09-19` (Sat) returns `slot: null` and the next planned date;
`/day/2026-13-40` → 400.

### Choices I made that were not specified
- **`week_minutes` is carried on every objective row** (cross join) rather than a
  second query, to keep NFR-03's one-query promise. `today_minutes` and
  `extra_off_day_minutes` are summed in the pure assembler from the same rows.
- **The segment "in force" on the date** is chosen as the one whose range covers
  the date, else the latest by seq (so an out-of-plan date still shows a
  schedule, with `slot: null`).
- **`next_planned_date`** = the next day-slot strictly after the date. Computed in
  the same query.
- **`last_deviation` is always `null`** — the deviation table is a later story.
- **`extra` per entry** = no `day` slot covers its `local_date` (contract wording),
  computed in SQL.
- **Zero active objectives ⇒ zero totals** (nothing to carry `week_minutes`). An
  acceptable edge for now; noted so it is not mistaken for a bug.

### ADR / contract friction
- The contract's `Day` has `period_logged_minutes` (for week slots) on
  `DayObjective`; with only fixed (day) slots seeded it is omitted. No change to
  the contract — the field is optional.
- Nothing in the contract was contradicted.

### For your review-gate answer (why one query, not one per objective) [W3-13]
You need: NFR-03 caps the Today read at one round trip (p95 < 300 ms). One query
per objective is N+1 — it grows with the number of objectives and blows the
budget, and it makes "the totals" a second pass. The single query joins
objectives → their covering slot → the date's entries and computes the totals in
the same statement, so cost is one round trip regardless of objective count.
Evidence to point at: `getDayRows` issues exactly one `query(...)`; the route
calls the service once; the CTE structure in `repo.ts`.
