  `"user"`, `objective`, `plan_segment`, `plan_slot`, `effort_entry`, four enum

- `npm run migrate` / `migrate:down` (`scripts/migrate.mjs`) and `npm run seed`
  (`scripts/seed.mjs`).
- Seed: one user (fixed id = `DEFAULT_SEED_USER_ID`), one objective "Ship Keel"

  (2026-09-14 … 2026-10-11). Idempotent (`ON CONFLICT DO NOTHING`).
- `src/modules/objectives/domain/generateSlots.ts` (+ test) — pure, fixed-mode
  slot generation. `weekdays.ts` — bitmask↔array helpers.
- `src/shared/db.ts` — the one pg `Pool` + `query` helper (repo.ts uses it).
- `src/config/env.ts` — added `seedUserId` (defaults to the seeded user).

### Choices I made that were not specified
- **Table `"user"` kept its ERD name** (reserved word, quoted everywhere) rather
  than renaming to `app_user`. Faithful to the ERD; the cost is quoting.
- **`password_hash` is nullable.** Auth is E-06; inventing a credential now was
  off-limits, so the column exists but is empty on the seed user.
- **`from_parked_idea_id` and `created_by_review_id` are plain uuid columns with
  no FK yet** — the tables they reference (`parked_idea`, `review`) are later
  stories. FKs land with those tables.
- **Enums as real Postgres enum types** (`review_cadence`, `objective_status`,
  `schedule_mode`, `period_kind`) rather than text + CHECK.
- **Non-overlap invariant (4) enforced by an `EXCLUDE` constraint** (needs
  `btree_gist`). Contiguity ("no gaps") is *not* expressible as a cheap
  constraint and is left to the app — noted so it is not mistaken for enforced.
- **`generateSlots` implements fixed schedules only**; flexible/week generation
  throws (the seed uses a fixed segment). Flexible arrives with its story.
- **Migrations are `.cjs` raw SQL** via `pgm.sql`, not the JS builder API —
  clearer and closer to what actually runs. Migration SQL is not "repo.ts", so
  ADR-001's "SQL only in repo.ts" is not violated.

### ADR / ERD / contract friction
- Nothing wrong in the ERD. The ERD says these five tables and this is what was
  built. The contract isn't exercised yet (no endpoint in this story).

### For your review-gate answer (why local_date and logged_at are separate) [W3-12]
You need: the two answer different questions — `local_date` is *the day the user
meant* (a calendar date, set by the client, never moved — NFR-12 / invariant 2),
`logged_at` is *the instant the row was written* (a timestamptz, server clock).
`tz` records the zone it was logged in. An entry logged at 00:30 for the previous
evening's work must keep the previous day; deriving the day from `logged_at`
would move it. They are separate columns because one is not derivable from the
other. Evidence to point at: the three columns in `effort_entry`, and that
W3-14 takes `local_date`/`tz` from the request body, never from `now()`.

## W3-13 — GET /day/{date}

### What exists now
- `GET /day/{date}` (`src/app/day/[date]/route.ts`) returns the contract's `Day`
  shape against real rows. Validates the date (400 on a bad one), 503 if the DB
  is unreachable. No auth (E-06) — the user is the seeded user, via the service.
- `src/modules/today/repo.ts` — the **one** SQL query.
- `src/modules/today/domain/assembleDay.ts` (+ test) — pure: shapes rows into
  `Day`, sums the totals. `rows.ts` holds the row shape (on the domain side so
  the assembler can import it without importing repo).
- `src/modules/objectives/domain/scheduleLabel.ts` (+ test) — the schedule
  label ("FIXED · MON–FRI · 2h 00m PER DAY").
- `src/shared/contract.ts` — typed DTOs for the contract. `src/shared/http.ts` —
  json / problem (RFC 9457) response helpers.

### The query, and the query count
**One query per request.** `getDayRows` issues a single statement (CTEs: active
objectives → covering segment → covering slot → the date's entries with a
per-entry `extra` flag → week-to-date total → next planned date), returning one
row per active objective. The app never loops over objectives issuing more
reads. Verified live: `/day/2026-09-16` (planned Wed) returns the slot + label;
`/day/2026-09-19` (Sat) returns `slot: null` and the next planned date;
`/day/2026-13-40` → 400.

### Choices I made that were not specified
- **`week_minutes` is carried on every objective row** (cross join) rather than a
  second query, to keep NFR-03's one-query promise. `today_minutes` and
  `extra_off_day_minutes` are summed in the pure assembler from the same rows.
- **The segment "in force" on the date** is chosen as the one whose range covers
  the date, else the latest by seq (so an out-of-plan date still shows a
  schedule, with `slot: null`).
- **`next_planned_date`** = the next day-slot strictly after the date. Computed in
  the same query.
- **`last_deviation` is always `null`** — the deviation table is a later story.
- **`extra` per entry** = no `day` slot covers its `local_date` (contract wording),
  computed in SQL.
- **Zero active objectives ⇒ zero totals** (nothing to carry `week_minutes`). An
  acceptable edge for now; noted so it is not mistaken for a bug.

### ADR / contract friction
- The contract's `Day` has `period_logged_minutes` (for week slots) on
  `DayObjective`; with only fixed (day) slots seeded it is omitted. No change to
  the contract — the field is optional.
- Nothing in the contract was contradicted.

### If you have ten minutes
Read `src/modules/today/repo.ts` (the one query) alongside NFR-03, then
`assembleDay.ts` to see the SQL/domain split.

### For your review-gate answer (why one query, not one per objective) [W3-13]
You need: NFR-03 caps the Today read at one round trip (p95 < 300 ms). One query
per objective is N+1 — it grows with the number of objectives and blows the
budget, and it makes "the totals" a second pass. The single query joins
objectives → their covering slot → the date's entries and computes the totals in
the same statement, so cost is one round trip regardless of objective count.
Evidence to point at: `getDayRows` issues exactly one `query(...)`; the route
calls the service once; the CTE structure in `repo.ts`.

## W3-14 — POST effort entry

### What exists now
- `POST /objectives/{objectiveId}/effort-entries`
  (`src/app/objectives/[objectiveId]/effort-entries/route.ts`) per the contract.
  201 → `EffortEntry`; 400 (bad body), 404 (no such objective / not yours),
  422 (not active, or date outside every segment), 503 (DB down).
- `effort/domain/validateWrite.ts` (+ test) — pure body validation; a
  client-sent `extra` is ignored, never stored.
- `effort/repo.ts` — `checkObjectiveForEffort` (status + date-covered) and
  `insertEffortEntry` (RETURNING computes `extra` and `logged_at` server-side).
- `effort/service.ts` — validate → 404/422 rules → insert. Replaces the W3-09
  scaffolding stub.

### Verified live
POST on a planned Wed → 201, `extra:false`. POST on a Sat inside the segment
range but not a planned weekday → 201, `extra:true`. `GET /day/2026-09-16` then
shows the entry (logged_minutes 90; week 120). Date outside the plan → 422;
unknown objective → 404; empty body → 400 naming each field.

### Choices I made that were not specified
- **`logged_at` is the DB `now()`**, set in the INSERT — never from the client,
  never from the body.
- **`extra` is computed in the INSERT's RETURNING** (no day slot covers the
  date), so the 201 body carries the same derived value GET /day would show.
  It is never a column and never read from the request.
- **Two queries for the write** (check, then insert). NFR-03 constrains the
  Today *read*, not writes; keeping them separate is clearer than one clever
  statement.
- **"Outside the plan" = outside every segment's date range.** A date inside the
  range but not a planned weekday is accepted and is `extra` — matching the
  contract note on GET /day ("logging is still allowed and counts as extra").
- **Bad objective id shape → 404** (not 400): consistent with NFR-10, a
  non-existent/foreign row is indistinguishable from not-found.

### ADR / contract friction
- None. The contract's 201/400/404/422/503 for this operation are all
  implemented as written.

### If you have ten minutes
`effort/repo.ts` `insertEffortEntry` — see `logged_at` defaulting to `now()` and
`extra` computed in RETURNING, the two places NFR-12 and the "extra is derived"
rule are enforced.

### For your review-gate answer (why the client sends local_date and tz) [W3-14]
You need: the server clock cannot know which *day* the user means. Work done at
23:55, or logged at 00:30 for the previous evening, or logged from a different
timezone than it happened in — in all of these the calendar day the effort
belongs to is the client's, not the server's. So `local_date` (the day) and `tz`
(the zone it was logged in) are sent by the client and stored verbatim;
`logged_at` (server `now()`) records when the row was written, separately. If
the server derived the day from request time, an entry near midnight or across a
zone would land on the wrong day and NFR-12 / invariant 2 would break. Evidence:
the route/service never read a clock for `local_date`; `insertEffortEntry` takes
`local_date`/`tz` from the validated body and only `logged_at` from `now()`.

## W3-15 — Today renders the slice

### What exists now
- `src/app/page.tsx` — the Today screen, a **server component** (D-04) that
  fetches `GET /day/{date}` from the real endpoint and renders objectives, their
  schedule label, the day's plan target, each entry (minutes, time, note, an
  `extra` badge) and the totals. `?date=` overrides the day for inspection.
- `src/app/loading.tsx` — the loading state (shown while the server render is in
  flight). `src/app/error.tsx` — the error boundary (client) as a safety net.
  The endpoint's own failure (DB down / bad date) is handled inline in the page
  as an error panel.
- `src/app/page.module.css` — CSS Modules, legibility only (no design work).

### Verified live
`/?date=2026-09-16` renders "Ship Keel", the schedule label, "Planned today:
2h 00m", the logged entry with its note, and totals (1h 30m). `/?date=not-a-date`
renders the "Couldn't reach your log" error state (the endpoint 400s → the page
shows the error state rather than a blank or a zero — NFR-07 in the UI).

### Choices I made that were not specified
- **The screen is `/` (home)**, replacing the walking-skeleton page.
- **The page calls the HTTP endpoint** (`fetch(appBaseUrl + /day/...)`) rather
  than the service directly, because the story says "from the real endpoint".
  It costs one in-process hop; the alternative (calling `getDay` directly) would
  not exercise the endpoint.
- **"Today" is the server's local date**, `?date=` overrides. Real per-user
  timezone resolution is NFR-12 (v2) and arrives with auth (E-06). Flagged so it
  is not mistaken for finished tz handling.
- **No logging form yet.** The story is "render the slice"; effort is created
  via the W3-14 endpoint. A form is a later story.
- Entry **notes are shown on screen** — that is the UI, and correct. NFR-11 only
  forbids note text in *logs*, not on the page.

### ADR / contract friction
- None. `Day` renders as declared.

### For your review-gate answer (every hop from click to the row) [W3-15]
You need the full path, in order:

**Logging effort (the write; the "click"):**
1. Client `POST /objectives/{id}/effort-entries` with a JSON body.
2. Route handler `src/app/objectives/[objectiveId]/effort-entries/route.ts` —
   checks the id shape, parses JSON.
3. `effort/service.ts createEffortEntry` — orchestrates.
4. `effort/domain/validateWrite.ts` — pure validation (→ 400 if bad).
5. `effort/repo.ts checkObjectiveForEffort` — one SQL read (→ 404 / 422).
6. `effort/repo.ts insertEffortEntry` — `INSERT … RETURNING`; `logged_at` = DB
   `now()`, `extra` derived.
7. A row in the **`effort_entry`** table. 201 with the `EffortEntry` returns.

**Showing it (the read/render):**
8. Browser requests `/` → `src/app/page.tsx` (server component).
9. It `fetch`es `GET /day/{today}` → route `src/app/day/[date]/route.ts`.
10. `today/service.ts getDay` → `today/repo.ts getDayRows` — the one query reads
    the row back → `today/domain/assembleDay.ts` shapes it.
11. The page renders the HTML server-side; the entry appears under its objective.
